# Architectural Decision Records (ADRs) Index

This document tracks Architectural Decision Records for the Cadence Clinical platform categorized by functional domain. Individual ADR files under `docs/adr/` are discovered directly from disk at build and validation time so parallel branches never contend over a central Markdown list.

## Standard ADR Template & Scaffolding

- [ADR Template](TEMPLATE.md)
- Scaffold a new ADR with `pnpm adr:new "<title>" --domain <domain> --req PRD-SYS-001` (or `dotnet run --project packages/cli/src/Cadence.Cli.csproj -- scaffold adr "<title>" --domain <domain> --req PRD-SYS-001`). It writes a self-contained `docs/adr/YYYY-MM-DD-<slug>.md` file with a deterministic date-and-slug hash identifier, canonical `- **Domain:**` metadata, `@req:PRD-...` traceability tags, and all six required sections—without modifying `docs/adr/index.md` or `docs/DOCUMENTATION_INDEX.md`.
- Validate with `pnpm cadence check adrs` (`dotnet run --project packages/cli/src/Cadence.Cli.csproj -- check adrs`).

## Numbering Rules

Every ADR has exactly one unique number, given on its first line as `# ADR-NNNN: Title` (numbers below 1000 keep their historical three-digit form, such as `ADR-049`). When a historical number was shared by several files, the oldest file kept it and later files were renumbered in date order with an `Also known as: ADR-XXX (former number)` line directly under the heading so older references still resolve. `check adrs` fails on duplicate numbers, a missing `# ADR-` heading, missing or invalid `- **Domain:**` metadata, invalid `@req:PRD-...` requirement tags, and any relative link across `docs/adr/*.md` that does not resolve.

New ADRs scaffolded via `pnpm adr:new` receive deterministic SHA-256 date-and-slug hash IDs in `10000–99999`, outside all historical manual area blocks (`001–2799`) and outside the closed `2800–2899` Stitch range, eliminating cross-branch renumbering conflicts.
