# ADR-[NUMBER]: Dynamic MSW Contract-Mocking Platform

* **Status:** Accepted
* **Date:** 2026-07-27
* **Authors:** @google-labs-jules[bot]
* **Deciders:** @fderuiter

---

## 1. Context & Problem Statement
Our frontend test suites previously maintained manual, fragile, and ad-hoc overrides of global network fetching (`globalThis.fetch` and `vi.fn()` configurations). This led to significant technical liabilities:
- **Silent API Drift:** Frontend mock models passed successfully in isolation even when the production backend gateway schemas evolved or experienced breaking contract shifts.
- **Maintenance Overhead:** Hundreds of redundant mock payload definitions were duplicated across the codebase.
- **Offline Constraints:** Local developer environments and Vitest runs suffered from a lack of reliable offline fallback routing when detached from live gateway instances.

To resolve these challenges, we need a unified interception framework capable of validating mocked payloads in real-time against actual backend OpenAPI schemas, with fallback mechanisms designed for offline resilience.

This decision implements requirements under PRD-EDC-007, PRD-EDC-008, and Trace-9.

## 2. Decision Drivers & Constraints
* **Driver 1:** Absolute alignment between frontend mocked requests/responses and current backend schema standards.
* **Driver 2:** High local developer velocity and offline capabilities.
* **Driver 3:** Zero-footprint client configuration (avoiding bulky generated SDK packages).

## 3. Options Considered
### Option 1: Generated Client SDK and TypeScript Signatures
* **Overview:** Compile backend OpenAPI specifications into static client-side TypeScript bindings and validate everything at compile time.
* **Pros:**
  * ✅ Catches standard type deviations at build time.
* **Cons:**
  * ❌ Increases bundle size and complicates the build step.
  * ❌ Does not intercept and validate raw, dynamic network responses/headers generated by third-party tooling or raw fetch commands.

### Option 2: MSW Network Interception with Real-Time Schema Assertions & Cascading Fallbacks [Selected]
* **Overview:** Intercept outgoing requests at the network layer using Mock Service Worker (MSW), then validate both request and response objects against live or cached schemas on-the-fly.
* **Pros:**
  * ✅ Complete coverage of all network boundaries (zero SDK dependency).
  * ✅ Real-time runtime checking of headers, path variables, query parameters, status codes, and JSON bodies.
  * ✅ Support for cascading fallbacks: attempts to fetch live schema from `/openapi.json`, falls back to local JSON cache (`cached-openapi.json`), and finally parses embedded OpenAPI blocks inside docs.
* **Cons:**
  * ❌ Requires initial test-environment interception setup and light schema validation runtime overhead.

## 4. Decision Outcome
* **Chosen Option:** Option 2
* **Justification:** Implementing MSW network interception ensures complete coverage of all network boundaries without restricting our choice of client libraries or generating static dependencies. The cascading resolution mechanism makes local test suites robust against internet disruption while keeping contract drift checks strictly active.

## 5. Consequences & Trade-offs
* **Positive Impact:** All frontend test mocks are now dynamically and automatically validated. Outdated mocks fail test execution immediately with descriptive contract violations.
* **Negative Impact / Technical Debt:** Requires keeping a cached copy of the OpenAPI schema or relying on local markdown documentation parsing for offline runs.
* **Mitigation Strategy:** Created a Python helper (`generate-cached-openapi.py`) to compile backend specifications and populate the cache.

## 6. Implementation & Verification
* **Affected Repositories / Services:** Interceptor and MSW configuration under `/app/tests/setup-msw.js`, Vite and Vitest configs, multiple legacy test files.
* **Verification Plan:** Validated via Vitest running with mock schemas. Running `python /app/scripts/validate_adrs.py` locally ensures ADR structure and coverage compliance.
