This does **not** actually satisfy the ticket's own AC for a non-object JSON payload (e.g. a bare `[1,2,3]` array): deserializing a JSON array into `Dictionary<string, object?>` throws a `JsonException` (token-type mismatch), it does not return `null`, so the design doc's `??`-based null-check would never fire for that case — the array's `JsonException` would instead fall into the generic catch clause and get wrapped with the _wrong_ message ("Demographics ciphertext could not be decrypted." instead of the AC's required "Decrypted payload was not a JSON object."). The implementation instead parses with `JsonDocument.Parse` first, explicitly checks `RootElement.ValueKind == JsonValueKind.Object` and throws the exact required message before attempting any dictionary conversion, then converts each property via a small recursive `JsonElement`-to-CLR-value switch (object/array/string/number-as-long-or-double/bool/null) so `Decrypt`'s return value contains genuinely comparable native types rather than boxed `JsonElement`s (which do not compare equal across separate `JsonDocument` instances, and would have made the round-trip AC untestable as literally specified). This is a from-the-ticket-necessitated correction to the design doc's sketch, not a scope deviation — the resulting behavior matches every one of the ticket's Acceptance Criteria exactly, including the specific message wording.
  - `DemographicsEncryptionOptions.KeyBase64` defaults to `string.Empty` (not `required`) to keep the options-binding shape conventional or ASP.NET Core configuration binding; no divergence in behavior from the design doc, which does not specify a default.
  - Per the ticket's explicit boundary-check AC, the encryption key is never a literal in `AesGcmDemographicsEncryptionService.cs` — sourced exclusively via the constructor's `IOptions<DemographicsEncryptionOptions>` parameter, verified by code inspection (this AC is a code-shape constraint, not something a unit test can assert in isolation, matching how prior tickets' `TreatWarningsAsErrors`/`#nullable enable` ACs are verified at the build level rather than by a dedicated test).
