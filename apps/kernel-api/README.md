# Kernel API host

The Clinical Kernel's HTTP host ([ADR-2540](../../docs/adr/2026-09-30-kernel-api-host-and-read-endpoints-for-the-canvas.md)). It serves the kernel's read endpoints for the Clinical Canvas: navigation, dry-run authorization with explanations, the command catalogue, search, protocol versions, lineage and the activity stream. It is the only process that registers kernel persistence (K-XS-2); product services never reference it. Since ADR-2620 it also hosts the command pipeline for observation writes.

**Status:** the endpoints are mapped, documented and tested, and each read runs in the kernel tenant found from the tenant code the gateway signs. Authorization decisions come from the caller's grants, roles and delegations, and so does what the caller may see (ADR-2457): an object is visible when a grant in effect covers it, and masked in place otherwise, so a caller with no grant sees every object masked. Blinding and the IdentityVault (#4782) are not decided yet.

## Project

- Project: `apps/kernel-api/src/Cadence.Kernel.Host.csproj` (assembly `Cadence.Kernel.Host`).
- `Program.cs`: composition root. Registers kernel persistence, the scope graph and navigation, search, authorization, synchronous protocol design import (`ProtocolDesignImporterService`) and the activity stream, and maps `MapKernelApi().MapKernelReads().MapKernelStudyImports()` from `Cadence.Kernel.Api`.
- `ClaimsCurrentActor`: the acting person, from the verified `sub` claim. A subject the kernel does not accept as an accountable person (`system`, `admin`, a `svc:` or `agent:` id) gives no actor, so dry runs deny with `actor.resolved`.
- Authorization: the kernel's `AuthorityEvaluator` (`AddKernelAuthorityEvaluator`, ADR-2455), with no platform operators, except the development tenant bootstrap's service account when `Kernel:DevelopmentTenant:Code` is set in Development (ADR-2542). Without a grant in effect covering the resource, a decision is a denial whose unmet condition is `grant.active`.
- `DevelopmentTenantBootstrap` (ADR-2542): in Development, with `Kernel:DevelopmentTenant:Code` set, provisions that tenant on start through the command pipeline as `svc:kernel-development-bootstrap`, the host's only platform operator, unless an active tenant already has the code. docker compose and the AppHost set `cadence-local`, the code the local realm's users sign in with (ADR-2514). The host refuses to start with the setting in any other environment.
- `DevelopmentDemoData` (ADR-2543, ADR-2549): with `Kernel:DevelopmentTenant:DemoData` also true, the bootstrap loads the canonical study, sponsor, sites, participants, roles and user grants from embedded `packages/demo-fixtures/demo-seed.json` via source-generated `System.Text.Json` and writes the demo study `CADENCE-101` into that tenant through the pipeline (a sponsor, `SITE-101` and `SITE-102` with their institutions, an approved and effective protocol v1 with scheduled and unscheduled `CollectionSpec`s and activated study sites, and three screened participants) and grants each user of `docker/cadence-realm.json` a role by their fixed subject id: `crc.site101`, `pi.site101` and `cra.monitor` at the `SITE-101` study site, everyone else on the whole study. It first grants itself a tenant-wide `DEMO_SEEDER` role for those writes. Ids, timestamps and idempotency keys are fixed, so a restart replays every command and writes nothing new. docker compose and the AppHost turn it on.
- `DirectoryTenantResolver`: finds the caller's kernel tenant from the signed `tenant_id` claim through `ITenantDirectory.FindActiveByCodeAsync`. A missing code, or one that names no active kernel tenant, is a 403; there is no fallback tenant and no configured mapping.
- `KernelDatabaseHealthCheck`: the readiness probe opens a connection to the kernel database.
- `KernelMigrationHostedService`: applies the kernel migrations on start when `Database:MigrateOnStartup` or `Database:MigrateOnly` is set, then each module's (`AddModuleMigrations`, in its own schema).
- The Intelligence module ([`apps/intelligence`](../intelligence/README.md), ADR-2630): `AddCadenceIntelligenceModule` and `MapIntelligenceModule()` add the AI agent runtime, its ledger and controls, and the command-palette intent router under `/api/v1/ai`.
- The Execution module ([`apps/execution/module`](../execution/module/README.md), ADR-2622): `AddCadenceExecutionModule` and `MapExecutionModule()` add eCRF forms over kernel form instances under `/api/v1/execution/forms`. `KernelReadAccess` gives module reads the kernel's masking (`IKernelReadAccess`).
- The activity projector (`AddKernelActivityProjection()`, ADR-2485): copies committed kernel events into the activity stream every five seconds. This is the one host with kernel persistence, so it runs the projector (ADR-2540 §4.7).

The endpoints, response records and tenant filter live in [`packages/kernel/src/Cadence.Kernel.Api`](../../packages/kernel/README.md).

## HTTP surface

All reads are `GET`, need the gateway-signed caller identity, run in the caller's kernel tenant, and answer RFC 9457 problem details on failure. The wire is snake_case. Objects the caller may not see are masked (ADR-2471): node reads, paths and child lists keep them in place with only `kind` and `mask`; search leaves them out; lineage reads keep them as a `masked:n` handle with their kind and count them like any other.

### Self-service trial onboarding (ADR-2547, ADR-2552, ADR-2605, ADR-2823)

`POST /api/v1/kernel/onboarding/trial` runs outside `KernelTenantFilter` (protected by `SignedInCallerPolicy`, without `.AllowExpiredTenantWrite()`) so newly self-registered Keycloak users with no existing `tenant_id` claim, foreign `TenantMembership`, or clinical roles (`403 K.Commercial.OnboardingCallerInvalid`) can bootstrap an isolated trial workspace (`organization_name`, `tier`, `residency`) with caller-supplied `Idempotency-Key` and signed `X-Change-Reason`. `TrialOnboardingService` executes idempotently per OIDC `sub` under platform operator `svc:kernel-trial-onboarding` (`KernelAuthorityOptions.TrialOnboardingOperator`), dispatching kernel commands to provision the `Tenant`, sponsor `Organization`, starter `SiteInstitution`, default sandbox `Site`, pseudonymous `Person`, `TenantMembership`, initial `sponsor_admin`, `sponsor_designer`, and `site_investigator` `Role` and `Grant` records (excluding commercial operator capabilities `subscription.activate`, `subscription.expire`, `entitlement.grant`, and `entitlement.revoke`, plus granting `participant.register` alongside `execution.form.open` on the `execution-forms` module service account), the delegable `TRIAL_DATA_MANAGER` role template, and bitemporal `SubscriptionPeriod` (`Trialing`) + `ProductEntitlement` rows (`Blueprint`, `Capture`, plus tier-included families), then writes `tenant_id`, explicit `site_id` (starter sandbox site), empty initial `study_ids` (never wildcard `*`), and realm roles (`Sponsor Admin`, `Sponsor Designer`, `Site Investigator`) back to Keycloak (`ADMIN_EDIT`) fail-closed (`502 K.Commercial.IdentityProviderSyncFailed`) via `KeycloakOnboardingClient`.

### Study creation, site setup & synchronous protocol draft import (ADR-2476, ADR-2552, ADR-2823)

| Route (`/api/v1/kernel/…`)                 | Does                                                                                                                                                                                                                                                                                                                          |
| ------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `POST organizations`                       | Registers an organization (`organization.register`, `Sponsor` or `SiteInstitution`) with `Idempotency-Key` and signed `X-Change-Reason`.                                                                                                                                                                                      |
| `GET sites`                                | Lists visible investigational sites in the caller's tenant (`IStudyDirectory`, optional `institution_ref` and `country` filters), filtered by `INodeVisibility`.                                                                                                                                                              |
| `POST sites`                               | Registers an investigational site (`site.register`) with a 2-letter ISO country code under an existing or newly registered `SiteInstitution` (`organization.register`, disambiguating colliding sponsor codes with `-SITE`) and synchronizes `site_id` scope via `IKernelIdentityScopeSynchronizer`.                          |
| `POST studies`                             | Registers a study (`study.register`), optionally registers its sponsor (`organization.register`) and links the starter/selected site in one step (`study.link_site` via `link_sandbox_site` / `initial_site_ref`), and synchronizes explicit `study_ids` (and linked `site_id`) scope via `IKernelIdentityScopeSynchronizer`. |
| `GET studies/{studyRef}/sites`             | Lists visible sites linked to a study (`StudySite` directory entries with institution metadata and activation status), refusing hidden studies with `403` and filtering entries by `INodeVisibility`.                                                                                                                         |
| `POST studies/{studyRef}/sites`            | Links an investigational site to a study (`study.link_site`) by `site_ref` or `site_code` with `Idempotency-Key` and signed `X-Change-Reason` (`409 K.StudySite.DuplicateSite` if already linked) and synchronizes `site_id` scope via `IKernelIdentityScopeSynchronizer`.                                                    |
| `POST studies/{studyRef}/protocol-imports` | Synchronously imports an ODM v1.3.2 XML file, a USDM v4 JSON file, or bundled CDISC Library eCRF templates into a `Draft` protocol version (`CreateProtocolDraft`, `ReviseProtocolDraft`, or `ForkProtocolVersion` + `ReviseProtocolDraft`). Enforces a 10 MB limit and blocks DTDs.                                          |

### Observation writes (ADR-2620)

The host also runs the kernel command pipeline (`AddKernelCommandPipeline`), so a write commits its state, audit chain link, event and outbox row in one PostgreSQL transaction. After commit, its background jobs relay the outbox to the in-process event consumers and seal the audit chains, each under a PostgreSQL leader lock so that one replica runs a job at a time (ADR-2601). Each write needs an `Idempotency-Key` header and takes its reason for change only from the gateway-signed identity (`X-Change-Reason`, ADR-2495; `SignedChangeReason`). Each is authorized against the observation's enrollment.

| Route (`/api/v1/kernel/…`)              | Does                                                                                                                                                                                                                                                                                                                                         |
| --------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `POST observations`                     | Records an observation (`observation.record`): enrollment, concept, typed value (ADR-2623, for example `{"type":"quantity","value":182,"unit":"mm[Hg]"}`), observed-at. 201; 422 `K.Observation.ValueInvalid` for a value that fails its kind's rules; 409 `K.Observation.ParticipantWithdrawn` once the participant is withdrawn (audited). |
| `POST observations/{ref}/corrections`   | Corrects the value (`observation.correct`) with the expected version. 409 `K.Observation.VersionStale`, 423 `K.Observation.Locked`, 422 `K.Command.ReasonForChangeRequired` without a reason (the pipeline's check, as for every kernel mutation).                                                                                           |
| `POST observations/{ref}/verifications` | Verifies an observation's current revision against source (`observation.verify`, `VerifyObservation`). 201; 409 `K.Assertion.RevisionStale`, 423 `K.Assertion.Locked` (Frozen still allows SDV), 422 without a reason.                                                                                                                       |
| `POST assertions/{ref}/retraction`      | Withdraws an active assertion (`assertion.retract`, `RetractAssertion`) by recording a retracting assertion. 200; 409 `K.Assertion.AlreadyRetracted`, 423 `K.Assertion.Locked`, 422 without a reason.                                                                                                                                        |
| `GET observations/{ref}`                | The value, version, the locks covering it (ADR-2621), every revision, the assertions about it and the kernel audit entries. 403 when the caller may not see its enrollment.                                                                                                                                                                  |

### Signed locks and streaming clinical exports (spec §10.1, §10.5)

Applying or releasing a clinical lock requires an `Idempotency-Key`, a signed `X-Change-Reason`, and a fresh single-use 60-second `X-Sig-Token` (21 CFR Part 11). `ApplyLock` and `ReleaseLock` validate target existence, duplicate locks, and lock readiness before recording the `Attestation` over the canonical `LockStatement` atomically inside the `StudyId`-authorized command transaction, leaving zero orphan `Attestation` rows on rejected writes. `Locked` assertions require zero open `Queried` assertions, zero missing required `CollectionItem`s, and zero unresolved `Error` validation findings (`409 K.Assertion.ScopeNotReady` with a structured `Explanation`); `Frozen` remains available while sites answer and monitors close queries. Study exports and participant casebooks project canonical bitemporal kernel state at `as_of(valid_at, known_at)` (`K-TRUTH-1`), exclude `IdentityVault` direct identifiers, and emit explicit `masked` placeholders for unauthorized sites or blinded treatment values (`K-AUTH-4`).

| Route (`/api/v1/kernel/…`)                                   | Does                                                                                                                                                                                                                                                                                                                                         |
| ------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `POST locks`                                                 | Applies a `Frozen` or `Locked` assertion (`lock.apply`) across `study`, `study_site`, `enrollment`, `collection_instance` or `observation` after validating readiness and `X-Sig-Token`, recording the step-up `Attestation` atomically.                                                                                                     |
| `POST locks/{lockRef}/release`                               | Releases an active lock (`lock.release`) with a step-up signed retracting assertion and atomic `Attestation`.                                                                                                                                                                                                                                |
| `GET studies/{studyRef}/locks?as_of=&active_only=`           | Lists locks recorded for a study at an optional bitemporal `as_of` coordinate, masking unauthorized or blinded scopes in place.                                                                                                                                                                                                              |
| `GET studies/{studyRef}/locks/readiness?scope_ref=`          | Evaluates whether a target scope is ready for `Locked`, returning open-query, missing-required-item, and open-error-finding counts, masked per-blocker ownership/next actions (`K-AUTH-4`), and a structured `Explanation`.                                                                                                                  |
| `GET studies/{studyRef}/exports?format=&lock_filter=&as_of=` | Streams a bitemporal study snapshot as `csv`, `odm_xml` (ODM v1.3.2 `MetaDataVersion` + `ClinicalData`), `dataset_json` (Dataset-JSON v1.1.0), `sas_bundle` (ZIP with CSV + `.sas` + `manifest.json`), `r_bundle` (ZIP with CSV + `.R` + `manifest.json`), or `study_archive` (ZIP regulatory archive with per-enrollment `%PDF-1.7` eCRFs). |
| `GET enrollments/{enrollmentRef}/casebook?format=&as_of=`    | Streams a participant casebook (`json`, `odm_xml`, printable `html`, or certified `%PDF-1.7` `pdf`) with revisions, queries, verifications, `Attestation` signatures, and `X-Content-Sha256` digests.                                                                                                                                        |

### Execution forms (ADR-2622)

`POST /api/v1/execution/forms`, `GET /api/v1/execution/forms/{formId}` and `PUT /api/v1/execution/forms/{formId}/values` open, read and save eCRF forms; the [Execution module README](../execution/module/README.md) describes them.

### Proposals (ADR-2635)

Proposals an agent or a person made (ADR-2489), for the Canvas's Needs Attention and review screen. A proposal, its plan and each affected object the caller may not see stay in place with their mask (ADR-2471).

| Route (`/api/v1/kernel/…`)                        | Does                                                                                                                                                                                                                |
| ------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET studies/{studyRef}/proposals?status=&limit=` | The study's proposals, newest first. `status` is `Open`, `Approved`, `Rejected`, `Withdrawn` or `Expired` (an open proposal past its expiry); `limit` is 1 to 200 (default 50). A hidden study is refused with 403. |
| `GET proposals/{ref}`                             | One proposal: intent, plan, affected objects, requested capabilities, proposer and kind, model, confidence, content hash, status and decision. 403 when the caller may not see it.                                  |
| `POST proposals/{ref}/rejection`                  | Rejects an open proposal (`proposal.reject`) with the signed reason for change and an `Idempotency-Key`. 409 `K.Proposal.NotOpen` or `K.Proposal.Expired`; 422 without a reason. Approval waits on #5552.           |

Also `GET /healthz`, `/healthz/live`, `/healthz/ready` and `GET /api/v1/kernel/status` (anonymous). OpenAPI and the Scalar reference are mapped in Development only as named per-module documents (`/openapi/{document}.json`); the exported contracts are [docs/openapi/kernel_openapi.json](../../docs/openapi/kernel_openapi.json), [docs/openapi/intelligence_openapi.json](../../docs/openapi/intelligence_openapi.json), and [docs/openapi/execution_forms_openapi.json](../../docs/openapi/execution_forms_openapi.json).

The gateway forwards `/api/v1/kernel/**`, `/api/v1/ai/**` and `/api/v1/execution/forms/**` here. Compose publishes host port 8018 (container port 8080); the gateway's default upstream is `http://localhost:8018` (`KERNEL_SERVICE_URL`).

## Security

`AddCadenceSecurity()`, `AddCadenceBiometricLiveness()`, and `UseCadenceSecurity()` from [packages/security](../../packages/security/README.md): every route not marked anonymous requires the gateway-signed caller identity, and both `GATEWAY_SECRET` ([ADR-2256](../../docs/adr/2026-09-29-fail-closed-gateway-identity-and-signed-caller-authentication.md)) and `CADENCE_BIOMETRIC_LIVENESS_KEY` (base64 of 32 bytes, shared with `econsent` for `POST /api/v1/ai/biometrics/verify-liveness`, [ADR-2660](../../docs/adr/2026-11-23-biometric-liveness-hmac-key-and-single-use-replay-protection.md)) are required at startup. The tenant and the actor come only from the verified claims. Authorization is the kernel's own `KernelAuthorization` (K-AUTH-7); dry runs go to the authorization access log, not the audit chain (ADR-2483).

## Persistence

`AddKernelPersistence` with the connection string from `ConnectionStrings:cadence`, then `POSTGRES_CONNECTION_STRING`; startup fails without one (ADR-2260). Every read runs through a context bound to the caller's tenant by Row-Level Security ([ADR-2250](../../docs/adr/2026-09-29-kernel-tenant-isolation-via-row-level-security.md)). In production the host connects as the application role and the migrations and role grant are applied separately with `KernelDatabase`; docker compose and the AppHost connect as the schema owner and set `Database__MigrateOnStartup=true`.

## Tests

- `tests/Cadence.UnitTests/Gateway/GatewayRouteCoverageTests.cs` checks the gateway route against the endpoints this host maps; `tests/Cadence.UnitTests/AppHost/AppHostModelTests.cs` checks its port.
- The kernel ports themselves are tested against PostgreSQL in `tests/Cadence.IntegrationTests/Kernel`; the Execution module's forms through this host in `tests/Cadence.IntegrationTests/Execution/ExecutionFormHostPostgresTests.cs`.
- `tests/Cadence.IntegrationTests/Kernel/KernelDevelopmentTenantPostgresTests.cs` starts the real host on PostgreSQL as the application role with a development tenant code: the tenant is provisioned once, with an audit entry naming the bootstrap's service account, a caller with that code is served, and other codes are still refused. With demo data on, the coordinator finds `CADENCE-101` and lists their own site's participants while the other study site is masked, a person with no grant finds nothing, the grantees are exactly the realm's subject ids, and a second start adds no audit entry. `KernelApiHostTests` checks that the setting stops the host outside Development.
- `tests/Cadence.E2ETests/Journeys/CrossModuleJourneyTests.cs` runs the cross-module clinical journeys through this host on PostgreSQL as gateway-signed callers (#5471), with the host's modules migrated as it registers them: enrollment, forms opened, saved and read over the Execution module's routes, a query raised, answered and closed, SDV and the database lock; an SAE captured on the adverse event form, published under the same participant and corrected; and a withdrawal after which earlier data stays readable. Consent, form signatures, the SDTM export and Safety's intake are dated TODOs naming their issues. Kernel commands this host has no route for yet reach it through a test-only signed relay (`KernelHostCommandRelay`).
- `tests/Cadence.IntegrationTests/Kernel/KernelApiHostPostgresTests.cs` boots the real host on PostgreSQL with nothing faked: a coordinator granted at one study site gets their enrollment, the design elements and the version from Trace, dependents and amendment impact, the other site's enrollment masked in place, and the changed elements with the schedule directives; a reader with no grant gets the same dependents counts with everything masked, and is refused the amendment's impact report, which describes the version's content (ADR-2475). The host's own projector fills the activity stream, where the coordinator sees their site's screening and the other site's masked, and a reader with no grant is refused the study's activity.

## Run locally

```bash
export GATEWAY_SECRET="<at least 32 characters>"
export CADENCE_BIOMETRIC_LIVENESS_KEY="$(openssl rand -base64 32)"
export ConnectionStrings__cadence="Host=localhost;Port=5432;Database=cadence;Username=cadence;Password=<password>"
export Database__MigrateOnStartup=true
dotnet run --project apps/kernel-api/src/Cadence.Kernel.Host.csproj --urls http://localhost:8018
```

The Aspire AppHost ([apps/apphost](../apphost/README.md)) and docker compose also run it on port 8018.
