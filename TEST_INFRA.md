# E2E Test Infra: Cadence Clinical Platform

## Test Philosophy

The Cadence Clinical Research Software Platform operates under stringent GxP (Good Clinical Practice) and 21 CFR Part 11 regulatory compliance mandates. To ensure high reliability, architectural decoupling, and complete auditability across all microservice boundaries, our end-to-end testing infrastructure uses an **opaque-box, requirement-driven, 4-tier methodology**.

### The 4-Tier Test Methodology

1. **Tier 1 — Category-Partition (Feature Coverage)**: Validates primary functional behaviors (happy paths) for every feature, module, and data model. Tests verify that normal inputs produce expected domain entities, database records, and API responses.
2. **Tier 2 — Boundary Value Analysis (BVA & Edge Cases)**: Tests boundary conditions, extreme input values, invalid data formats, missing fields, permission boundaries, optimistic concurrency collisions, and error handling paths.
3. **Tier 3 — Pairwise Matrix (Cross-Feature Combinations)**: Evaluates interactions across microservice boundaries. Tests verify that services interact exclusively through Anti-Corruption Layers (ACLs) using Pydantic DTOs and HTTP client interfaces without direct sibling database or domain model imports.
4. **Tier 4 — Workload / Real-World Scenarios (End-to-End Workflows)**: Simulates full clinical trial lifecycles—from protocol authoring in Designer to eCRF data capture in EDC Execution, CTMS site delegation, safety SAE reporting, offline eCOA sync, eTMF archival, and complete architecture verification.

### Core Architectural Principles

- **REST API-First & Microservice Decoupling**: Sibling database imports across microservice boundary paths are strictly prohibited. Microservices strictly own their domain models under `apps/<service>/src/domain/`. Inter-service communications use local consumer-owned Anti-Corruption Layer DTOs (`apps/<service>/src/domain/acl/`) transmitted via authenticated REST HTTP calls.
- **100ms Internal SLA**: All cross-service REST HTTP client requests via `httpx.AsyncClient` must execute within an internal 100ms SLA.
- **HMAC-SHA256 V2 Security**: Every inter-service HTTP request is authenticated via gateway signatures generated by `generate_gateway_signature` from `packages.security.signing`.
- **SQLAlchemy Boolean Filter Standard (Ruff E712)**: ORM queries MUST use `Column.is_(True)` or `Column.is_(False)` to produce clean `IS TRUE`/`IS FALSE` SQL queries.
- **Zero Core-Models Imports**: `packages/core-models` is completely eradicated; AST import linters verify zero references across `apps/`, `packages/`, `scripts/`, and `tests/`.

## Test Architecture & Runner Setup

### Test Execution Commands

Developers and automated CI pipelines invoke the test harness using `uv run` to guarantee virtual environment consistency across sandboxed environments.

```bash
# 1. Run full test suite in parallel using all available CPU cores
uv run pytest -n auto

# 2. Run full test suite with coverage enforcement (fails if total coverage < 80%)
uv run pytest -n auto --cov=apps --cov=packages --cov-fail-under=80

# 3. Verify code formatting with Ruff
uv run ruff format . --check

# 4. Run Ruff linting check
uv run ruff check .

# 5. Run code duplication scanner (checks for 15+ consecutive identical lines)
uv run python scripts/detect_duplication.py

# 6. Re-export and validate OpenAPI schemas
uv run python scripts/validate_schemas.py --export-dir docs/openapi

# 7. Execute complete GxP Compliance Sync (runs tests, updates RTM, stages docs)
uv run python scripts/sync_gxp.py
```

### Pytest Harness & Worker Isolation (`conftest.py`)

- **Parallel Execution (`pytest-xdist`)**: Tests run in parallel workers via `-n auto`. Each worker thread executes in an isolated environment with independent async event loops (`pytest-asyncio`).
- **Database Fixtures & Isolation**: Integration tests use isolated async SQLite memory databases (`sqlite+aiosqlite:///:memory:`) or mock session handlers per worker thread, ensuring complete test independence without shared state leakage.
- **HMAC V2 Gateway Signatures**: Microservice gateway auth testing uses canonical test signature helpers (`generate_gateway_signature`). Gateway authentication middleware (`GatewayAuthMiddleware`) validates requests in memory.
- **Low-Latency SLA Simulation**: REST HTTP client calls utilize `httpx.AsyncClient` with custom mock transport adapters (`httpx.MockTransport`) to verify async response handling and sub-100ms SLA enforcement.

### Docstring Requirement Tagging (`@req:`)

Every test function MUST include an explicit requirement traceability tag in its docstring. The RTM generator script scans docstrings for `@req:` markers to build the compliance matrix.

```python
async def test_execution_eligibility_acl_evaluation():
    """Validate execution eligibility service consumes local ACL DTO via gateway client.

    @req:PRD-SYS-009
    """
    client = DesignerClient(base_url="http://designer-service.internal")
    result = await client.get_eligibility_criteria("protocol_123")
    assert isinstance(result, DesignerEligibilityCriterionDTO)
    assert result.is_active.is_(True)
```

## Real-World Application Scenarios (Tier 4)

Tier 4 tests execute complex, end-to-end clinical workflows that span multiple microservices, security layers, storage backends, and regulatory validation pipelines.

### Scenario S1: Multi-Tenant Audit & Document Storage Pipeline

- **Description**: Verifies multi-tenant document ingestion, dynamic PDF watermarking (`packages.storage.watermark`), 21 CFR Part 11 electronic signature metadata construction (`packages.security.signature`), and immutable GxP audit logging (`packages.database.audit`).
- **Workflow**:
  1. User authenticates with tenant context `tenant_alpha` and uploads binary protocol document stream.
  2. Storage module embeds dynamic security watermark with tenant name, upload timestamp, and user ID.
  3. `SignatureBuilder` attaches cryptographic manifest signature.
  4. Database layer records audit entry with UTC ISO timestamp, `created_by`, `reason_for_change`, and `version_index`.
- **Verification**: Query audit ledger, download stored document, verify watermark overlay text and signature validity.

### Scenario S2: Protocol Authoring to eCRF Specification Flow

- **Description**: Simulates clinical trial protocol authoring in Designer (`apps.designer.domain.usdm`), Schedule of Activities (SoA) matrix generation, eligibility criteria rule compilation, OpenAPI schema export, and ACL consumption by EDC Execution.
- **Workflow**:
  1. Author creates USDM v3.0 protocol definition with 3 arms, 5 visits, and 10 eligibility criteria.
  2. Designer compiles protocol narrative template into Jinja2/HTML/PDF via `DocumentRenderer`.
  3. Schema validator exports OpenAPI specifications to `docs/openapi`.
  4. Execution service queries Designer REST API; gateway client deserializes criteria into `DesignerEligibilityCriterionDTO`.
- **Verification**: Confirm zero USDM schema validation errors, verify OpenAPI exported files, test `DesignerEligibilityCriterionDTO` parsing in Execution.

### Scenario S3: Expedited SAE Reporting & Emergency Unblinding Workflow

- **Description**: Simulates subject adverse event logging in EDC Execution (`apps.execution`), escalation to Serious Adverse Event (SAE), E2B(R3) XML safety report generation in Safety service (`apps.safety.src.domain.sae_icsr`), and emergency treatment unblinding.
- **Workflow**:
  1. Clinical investigator submits eCRF Adverse Event form for subject `SUBJ-101`.
  2. Escalation trigger passes event data to Safety service via REST API.
  3. Safety service builds ICSR case, maps MedDRA reaction terms, and formats E2B(R3) XML export.
  4. Medical monitor requests emergency unblinding; system verifies RBAC role, logs audit event, and reveals treatment arm.
- **Verification**: Validate E2B(R3) XML schema conformity, verify unblinding audit record (user ID, timestamp, reason), confirm notification dispatch.

### Scenario S4: Site Activation & Delegation of Authority Management

- **Description**: Tests clinical trial site setup in CTMS (`apps.ctms.src.domain.doa_models`), Delegation of Authority (DOA) matrix assignment, electronic staff signatures, REST-based PDF document rendering via `DocumentRendererDTO`, and eTMF archiving.
- **Workflow**:
  1. Principal Investigator (PI) sets up site `SITE-001` and delegates tasks to Sub-Investigator and Study Coordinator.
  2. Delegated staff sign electronic signature manifests.
  3. CTMS queries Designer document rendering REST endpoint using local `DocumentRendererDTO` to produce signed DOA manifest PDF.
  4. Generated manifest is archived in eTMF investigator site binder (`apps.etmf`).
- **Verification**: Inspect CTMS delegation table, verify signature manifests, confirm `DocumentRendererDTO` deserialization, view generated DOA PDF.

### Scenario S5: Regulatory Inspection Readiness & eTMF Archival

- **Description**: Simulates site closeout and regulatory inspection audit prep. The eTMF service (`apps.etmf.src.domain`) scans binder completeness, checks staff certificate expiration dates, retrieves protocol version via `ProtocolVersionRefDTO` ACL, and locks binder (`HARD_LOCK`).
- **Workflow**:
  1. Trial coordinator initiates eTMF audit sweep for `SITE-001`.
  2. Expiration scanner checks document expiration dates against threshold.
  3. eTMF queries Designer REST API using local `ProtocolVersionRefDTO` to index active protocol version.
  4. eTMF binder status transitions to `HARD_LOCK`, preventing subsequent document mutations.
  5. Inspection archive ZIP is generated following TMF Reference Model v3.0 taxonomy.
- **Verification**: Confirm binder state is `HARD_LOCK`, verify 0 document mutation allowed, validate ZIP archive hierarchy and SHA-256 checksum manifest.

### Scenario S6: Offline eCOA Capture & Asynchronous Interoperability Sync

- **Description**: Simulates offline patient ePRO questionnaire completion on mobile device (`apps.interop.src.domain`), offline payload queuing, network reconnection, sync engine collision resolution, and gateway transport to EDC Execution.
- **Workflow**:
  1. Mobile app captures subject ePRO questionnaire responses offline and stores encrypted local payload.
  2. Network connection restores; payload posts to Interop Sync Engine.
  3. Sync engine validates device signature and delta timestamp.
  4. Interop service transmits payload to Execution service via REST HTTP client using `EPROTransportDTO`.
  5. Execution EDC database records subject ePRO submission.
- **Verification**: Confirm offline queue state transitions to `SYNCED`, verify `EPROTransportDTO` deserialization, verify eCRF form database insertion.

### Scenario S7: End-to-End Architecture Eradication & GxP Verification Flow

- **Description**: Full platform structural integrity check: verifies complete eradication of `packages/core-models`, runs AST import linters across all microservices, executes full test suite (`uv run pytest -n auto`), checks code style (`ruff check`/`format`), runs duplication scanner, and executes GxP RTM sync.
- **Workflow**:
  1. AST scanner verifies zero `import core_models` or `from packages.core_models` statements exist in codebase.
  2. Pytest executes full suite of 2,148+ tests in parallel mode.
  3. Ruff verifies zero linting and formatting violations.
  4. Duplication scanner checks all `.py` files for contiguous 15-line duplicate blocks.
  5. `scripts/sync_gxp.py` regenerates RTM and execution reports and stages them in git.
- **Verification**: Command `uv run python scripts/sync_gxp.py` exits 0 with zero uncommitted doc diffs and clean test report.

## GxP Compliance & Traceability Protocol

The Cadence Clinical Research Software Platform enforces automated compliance documentation synchronization. The GxP Requirements Traceability Matrix (RTM) and Installation/Operational/Performance Qualification (IQ/OQ/PQ) reports must reflect the exact current state of the test suite.

### Automated Sync Workflow (`scripts/sync_gxp.py`)

Whenever tests are added, renamed, or modified—or requirement docstring tags (`@req:`) are updated—developers and automated agents must run the unified GxP sync command:

```bash
uv run python scripts/sync_gxp.py
```

This single command executes a 3-step automated protocol:

1. **Test Execution**: Runs `uv run pytest -n auto --junitxml=report.xml` to produce an updated JUnit XML execution report.
2. **Matrix Generation**: Runs `uv run python scripts/generate_rtm.py` to parse `@req:` docstrings in test files and build:
   - `docs/SDLC/Requirements_Traceability_Matrix.md`
   - `docs/SDLC/IQ_OQ_PQ_Execution_Report.md`
3. **Git Staging**: Automatically stages the regenerated markdown files in git:
   ```bash
   git add docs/SDLC/Requirements_Traceability_Matrix.md docs/SDLC/IQ_OQ_PQ_Execution_Report.md
   ```

### CI Compliance Validation Gate

In CI pipelines, the GxP compliance check runs with `--dry-run`:

```bash
uv run python scripts/sync_gxp.py --dry-run
```

If any test docstrings or test execution results have changed without updating the checked-in RTM files, the command exits with code `1` and fails the build with:

```
GxP compliance documentation is out of sync with the current system state!
```

This ensures 100% auditability and strict compliance with 21 CFR Part 11 regulations.
